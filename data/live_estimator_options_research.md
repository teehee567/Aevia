# Live trajectory estimator options

Research date: 2026-09-06. Recommendation: prototype a bounded, fixed-lag **iterated error-state smoother** using the existing navigation model and a specialized chain solver. Keep the fast forward estimate for immediate output. This is a meaningful step beyond the current ESKF without requiring GTSAM as a dependency; its benefit and MCU cost still need measurement.

## Current implementation and target

The live core remains a 15-state, right-multiplicative ESKF with additional Schmidt/consider uncertainty and sample/gap cross-covariance bookkeeping. Its delayed fusion and present-state projection do not perform a backward smoothing pass. The live history ceiling is currently 500 ms; that is an arrival/fusion history limit, not evidence of a smoothing window. Sources: [`eskf.rs`](../traj/src/live/eskf.rs), [`live/mod.rs`](../traj/src/live/mod.rs), [`frontier.rs`](../traj/src/live/core/frontier.rs), [`predictor.rs`](../traj/src/live/predictor.rs).

The offline solver already contains backward smoothing and bounded IEKS iterations, including damping/objective checks. Its dynamic matrices, `f64` arithmetic and retained state/cross-covariance data make it an algorithmic reference, not a direct MCU implementation. Sources: [`smoothing.rs`](../traj/src/offline/solver/smoothing.rs), [`run.rs`](../traj/src/offline/solver/run.rs).

The specified ESP32-S31-WROOM-3-N16R16V is an **S31**, not an S3. Espressif's current preliminary module datasheet lists dual-core 32-bit RISC-V up to 320 MHz, 512 KB shared SRAM, 16 MB flash and 16 MB octal PSRAM for this variant. The project's live profile budgets 192 KiB internal SRAM, 1 MiB PSRAM and 32 KiB stack; these are whole-profile allowances, not available headroom. No runtime or memory fit is established here. Sources: [Espressif module datasheet, §§1.1–1.2](https://documentation.espressif.com/esp32-s31-wroom-3_wroom-3u_datasheet_en.html), [`resources.rs`](../traj/src/config/resources.rs).

## The useful middle ground

1. **Fixed-lag error-state RTS smoothing:** retain a bounded sequence of filtered/predicted states and their cross-covariances, then run backward after new observations arrive. Later GNSS observations can revise earlier attitude, bias, velocity and position through those correlations. This benefits recently completed trajectory and event estimates. The last state of a single RTS backward pass equals its input forward-filter endpoint: adding only this pass does not independently improve the current endpoint. The RTS initialization and recursion are documented in [JPL's square-root filtering and smoothing report](https://ipnpr.jpl.nasa.gov/progress_report/42-233/42-233A.pdf).
2. **Fixed-lag iterated error-state smoothing:** relinearize the retained nonlinear motion/measurement model around the improved trajectory and solve again, with a small iteration/work cap and accepted-cost-decrease checks. This can also change the window endpoint. IEKS has a Gauss–Newton interpretation; convergence and improvement are not unconditional. See [Lindqvist et al., Posterior linearisation smoothing with robust iterations](https://arxiv.org/abs/2112.03969).

For a Markov chain, the linearized solve is block tridiagonal: work is linear in the number of retained knots when state dimension is fixed. This is why a custom window can use fixed storage and a predictable schedule without a general graph engine. Shared consider variables and retained sample correlations in Aevia mean the actual system is richer than an independent 15-state chain; retain that structure, for example with an explicit small global border or augmented sufficient statistics. Do not discard those correlations to obtain a convenient solver. The chain/RTS equivalence is established by [Aravkin et al., Kalman smoothing and block tridiagonal systems](https://arxiv.org/abs/1303.5237); the application to Aevia is a design inference.

A reasonable experiment is a short window at GNSS/keyframe cadence, starting around 0.5–1 second and profiling before extending it. Propagate IMU continuously; summarize intervals with validated transition/covariance composition or bias-aware preintegration. Preintegration summarizes IMU readings between states, and bias corrections require appropriate Jacobians or reintegration. See [GTSAM's IMU factor documentation](https://borglab.github.io/gtsam/imufactor/). The proposed horizon and cadence are experiment settings, not measured capability claims.

## Correctness and output consequences

- Marginalize expired states into a boundary prior. Do not repeatedly use a posterior already containing retained observations as a prior and then fuse those same observations again. A marginalized nonlinear prior retains a linearization point; relinearizing other connected terms requires a deliberate consistency policy. GTSAM itself documents preserving boundary-variable linearization points for this reason. Sources: [FixedLagSmoother](https://borglab.github.io/gtsam/fixedlagsmoother/), [BatchFixedLagSmoother consistency field](https://gtsam.org/doxygen/a05859.html).
- Preserve manifold reset/tangent transport, Schmidt/consider semantics and shared-noise correlations through smoothing and marginalization. A naive ordinary RTS recursion over only the 15 navigation states is not automatically valid for this implementation. This is a repository-specific inference from its richer covariance structure.
- Distinguish the immediately predicted output, revisable recent trajectory, and committed historical result. A true smoothing lag can increase finalization latency beyond the existing arrival delay. Past values must remain revisable until they leave the window; smoothing a finalized segment only internally would not improve its published event result.

## Other candidates

| Change | Benefit it targets | Assessment for this project |
|---|---|---|
| Iterated ESKF measurement update | Better local fit to nonlinear observations | Smaller change; potentially modest gains for mostly linear GNSS position/vector velocity. It does not revise a trajectory window. |
| Invariant EKF | Symmetry-aware error dynamics and stronger local stability for applicable systems | Credible filter redesign when initialization or attitude linearization is the issue. A multiplicative quaternion ESKF alone is not an invariant navigation filter. Biases and lever-arm states require care. |
| Square-root filter/smoother | Numerical conditioning and covariance stability | Useful engineering improvement, especially when testing `f32`; it does not add observations or temporal reasoning. |

“Iterated” and “invariant” are separate ideas, despite both sometimes being abbreviated IEKF. They can be combined. Sources: [Barrau and Bonnabel, invariant EKF stability](https://arxiv.org/abs/1410.1465), [The Geometry of Navigation Problems, including biases and lever arms](https://arxiv.org/abs/2201.04426), [Iterated Invariant Extended Kalman Filter](https://arxiv.org/html/2404.10665v2), [Tracy, QR square-root Kalman filter](https://arxiv.org/abs/2208.06452).

For car GNSS PVT + IMU, expect the clearest opportunity in recent trajectory/event reconstruction, nonlinear attitude/bias corrections and short interruptions followed by useful GNSS. A different optimizer cannot create independent information, guarantee recovery from sustained biased GNSS, or eliminate inertial drift during a long unaided outage. Whether the extra nonlinear iterations beat this already elaborate ESKF is an empirical question. Compare current output, bounded RTS, bounded IEKS and the existing offline result on identical recordings; evaluate event error, uncertainty coverage, correction latency, worst-case execution time and actual SRAM/PSRAM/stack use.
