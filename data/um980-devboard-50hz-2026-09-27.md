# UM980 dev-board 50 Hz SPP test, 27 September 2026

Direct Python/pyserial test through CH340 on host COM8. No product firmware
was involved. The receiver identifies as UM980, R4.10Build14259, dated
2024/05/27. The antenna was indoors without sky visibility.

## Result

50 Hz BESTNAVA output works, but valid 50 Hz standalone positioning was not
demonstrated. The receiver explicitly rejects high-rate SPPNAVA requests in
signal group 8. Every captured position and velocity status was
INSUFFICIENT_OBS/NONE, with zero satellites used.

| Configuration | Request | Result |
|---|---|---|
| Group 1, 115200 baud | SPPNAVA 0.05 | Accepted; consecutive 50 ms receiver epochs |
| Group 1, 115200 baud | SPPNAVA 0.02 | Rejected: period unsupported |
| Group 8, 460800 baud, automotive, PVTALG AUTO | SPPNAVA 0.02 | Rejected: period unsupported |
| Same | SPPNAVA ONCHANGED | Rejected: grammar error |
| Same | SPPNAVA 0.05 | Rejected: period unsupported |
| Same | SPPNAVA 0.1 | Rejected: period unsupported |
| Same | SPPNAVA 1 | Accepted; 10 records/10 seconds, 1000 ms epochs |
| Same | BESTNAVA 0.02 | Accepted; 499 records/10 seconds, 498 consecutive 20 ms steps |

The final combined 10-second capture had zero CRC errors. An independent
15-second BESTNAVA capture had 749 records, 748 consecutive 20 ms steps and
zero CRC errors. Counts near the capture boundaries can differ by one.
Receiver timestamps are not synchronized to GPS indoors; their increments
prove message scheduling, not fresh valid position solutions.

## State left on the dev board

- Receiver COM1 through host COM8: 460800 baud, 8N1.
- CONFIG SIGNALGROUP 8 (this setting persists automatically).
- MODE ROVER AUTOMOTIVE; CONFIG PVTALG AUTO.
- COM1 output: BESTNAVA 0.02 plus SPPNAVA 1.
- No SAVECONFIG issued; baud, mode and log changes are volatile.
- Original state was signal group 1, MODE ROVER SURVEY, all UARTs 115200,
  and GPGGA/GPGSA/GPGST/GNGSV/GPRMC at 1 Hz on all three UARTs.

Switching signal group caused a delayed restart that reverted volatile
settings. The first baud-change attempt overlapped that restart; probing
found 115200 again. The successful test waited for restart, confirmed group
8 via CONFIG, then changed COM1 to 460800 and verified VERSIONA.

## Repeat the test

Install pyserial if needed:

```powershell
python -m pip install --target tmp/gnss-python pyserial
python tools/gnss-devboard.py --baud 460800 --seconds 10 --label outdoor --require-spp-50hz
```

The script records raw bytes and JSON summaries under tmp/gnss-devboard/.
It checks Unicore CRCs, receiver epoch increments, and both position and
velocity validity. Exit status 2 means valid SPP at 50 Hz was not observed;
an empty 50 Hz message stream cannot pass. No-command invocation only reads.
Use --probe to locate the baud rate after power cycling.

To restore the original signal group, send CONFIG SIGNALGROUP 1 at the
current baud, allow at least 15 seconds for restart, and probe again.
Since no SAVECONFIG was issued, the saved original output configuration is
expected to return on restart; verify CONFIG, MODE and LOGLISTA afterward.

## Firmware implication

The [Unicore N4 command manual R1.14](https://en.unicore.com/uploads/file/Unicore%20Reference%20Commands%20Manual%20For%20N4%20High%20Precision%20Products_V2_EN_R1.14.pdf)
records the addition of 50 Hz PVT output in the R1.6 revision history. Its
signal-group table (PDF page 73) describes 50 Hz positioning and velocity
for UM980 group 8. The installed May 2024 build predates that documentation
change. This supports investigating a compatible newer receiver firmware;
the manual does not identify the minimum build in that table, and this test
does not prove an upgrade will supply 50 valid SPP solutions per second.

A firmware compatible with this specific module and an outdoor capture
are needed to settle valid 50 Hz SPP. No receiver firmware was flashed.
